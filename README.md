# ポケアナ（ULA-4G36-72M）を Linux で使う

ELECOM のポケアナ 36（ULA-4G36-72M）を Linux から動かすツールです。この機械は Acute の PKLA の OEM です。メーカーのソフト（LA Viewer 1.90B07）は Windows（98SE〜Vista）でしか動きません。そこで、XP の仮想マシンで動かしたときの USB の通信を記録し、その形を読み解いて同じことをするようにしました（2026-11-18）。

- `pokeana.py`: 取り込みをして、ファイルに書き出します。
  - `.sr`（既定）: sigrok の形式です。PulseView や sigrok-cli で開けます。サンプリングの速さも入っています。トリガの位置は、足したチャンネル TRIG（トリガから後が 1）で示します。
  - それ以外の名前: VCD です。GTKWave で開けます。時刻 0 がトリガの位置です。PulseView の VCD の読み込みはマイナスの時刻を飛ばすので、PulseView には `.sr` を使います。
- `pokeana_gui.py`: GUI です（下の「GUI」）。
- `extract_replay.py`: 通信の記録（usbmon の pcap）から、起動の手順を取り出します。
- `decode.py`: 信号の解析（I2C、SPI、UART、CAN、パラレルバス）です。GUI から使います。コマンドでも、`.sr` を読んで結果を文字で出せます（下の「信号の解析」）。
- `tests/`: 解析を確かめるための道具です。`synth.py` は作った波形を、`atom_signals.py` は AtomS3U から出す試験の信号を作ります。

## GUI（作業用 PC のデスクトップで）

```
python3 ~/Claude/pokeana/pokeana_gui.py            # アプリ一覧の「ポケアナ」からも起動できます
python3 ~/Claude/pokeana/pokeana_gui.py cap.sr     # 保存したものを見る
```

- **上の行:** Run、連続（終わるとすぐ次を取る）、Stop（トリガを待つのをやめて、それまでの分を読む）、速さ、サンプル数、トリガ前（%）、しきい値（CH0〜17 と CH18〜35。「任意」で −6〜6V）、表示するチャンネル数、全体、保存（`.sr` か VCD）、PulseView で開く、が並びます。
- **トリガ:** チャンネル名をクリックするたびに、条件が「なし → ↑ → ↓ → ↕ → 1 → 0」と変わります。右クリックで「なし」に戻ります。条件はすべて同時に成り立ったときにかかります（AND）。
- **波形:**
  - ホイールで、マウスの位置を中心に拡大と縮小をします。Shift を押しながらのホイールか、ドラッグで左右に動きます。
  - 左クリックでカーソル A、右クリックでカーソル B を置きます。下の行に、A と B の時刻、差、その周波数が出ます。
  - 時刻 0 がトリガです（赤い線）。F キーで全体を、スペースキーで Run と Stop をします。
- **画面の例（`screenshots/`、実機で取り込んだもの）:**
  - `01_overview.png`: 20MHz、CH0 の立ち上がりでトリガ、全体表示。
  - `02_zoom_ch0_rise.png`: 同じものを拡大し、カーソル A と B を置いたところ（B−A 10µs、100kHz）。
  - `03_200MHz_ch3_rise.png`: 200MHz、CH3 の立ち上がりでトリガ。
  - `04_ch1_fall_pre50.png`: 10MHz、トリガ前 50%、CH1 の立ち下がりでトリガ。
- **ランチャ:** `pokeana.desktop` を `~/.local/share/applications/` に置いてあります。
- **必要なもの:** GTK 4 と python3-gi-cairo（作業用 PC には入れました）。
- **画面のない所で確かめるとき:** `gtk4-broadwayd :5` を立ち上げてから、`GDK_BACKEND=broadway BROADWAY_DISPLAY=:5 POKEANA_GUI_SHOT=out.png POKEANA_GUI_DO="rate 20000000;pre 10;cond 0 r;run;zoom 100"` で動かします（ほかに `depth`、`show`、`cursors`、解析の `dec i2c:scl=0,sda=1`、`list`、`goto 0`、`dialog 0`、解析の出し方の `place 0〜3`）。窓の絵が PNG に残ります。
  - `repeat 秒 [間隔]`: 「連続」で指定の秒数だけ取り続け、間隔（秒）ごとに PNG を `名前_月日_時分秒.png` で残します。

## 信号の解析（I2C、SPI、UART、CAN、パラレルバス）

GUI の「解析を追加」で、種類とチャンネルを選びます。

- **表示:** 解析の結果は、色分けした枠と 16 進の値で出ます。出し方は、上の行の選択で切り替えます。
  - 「解析を隠す」（はじめはこれ）: 波形だけを出します。一覧は使えます。
  - 「波形に重ねる」: SDA、MOSI、MISO、UART と CAN の RX の波形の上に、枠と値を重ねます。上位の解析の行は、その組のチャンネルのすぐ後に出ます。
  - 「信号のすぐ下」: 解析の行を、そのチャンネルのすぐ下に出します。
  - 「いちばん下」: 解析の行を、全チャンネルの下にまとめて出します。
  - 枠の幅に合わせて、文字は長いもの（`Address write: 0x50`）から短いもの（`50`）へ切り替わります。
  - 使っているチャンネルの名前の横には、役割（SCL、MOSI など）が出ます。
- **いくつも並べる:** 解析の数に上限はありません。I2C が 3 組（CH2/3、4/5、6/7）でも、I2C と SPI が混ざっていても、組ごとに 1 つずつ足します。
  - 解析の行の名前と一覧の見出しには、使っているチャンネルが付きます（`I2C 2/3`、`SPI MOSI 10-13`、`Flash 10-13`）。どの組の結果かが分かります。
- **設定の変更と削除:** 解析の行の名前か、チャンネルの名前の横の役割（SCL など）をクリックします。
- **一覧:** 「一覧」を押すと、右に解析した中身が時刻つきで並びます（I2C は 1 回の通信、SPI は CS の 1 区切り、UART は 1 行、CAN は 1 フレームごと）。行を選ぶと、波形のその場所を拡大して出します。
- **取り込みのたび:** 解析はやり直されます（「連続」でも動きます）。

| 種類 | 信号 | 設定 | 出るもの |
|---|---|---|---|
| I2C | SCL、SDA | これより短いパルスを無視する幅（はじめは 150ns） | Start / リピートスタート / Stop、アドレスと R/W、データ、ACK / NACK |
| SPI | CLK、MOSI、MISO、CS（MOSI、MISO、CS はなくてもよい） | モード 0〜3、MSB / LSB、ワードのビット数、CS の極性 | MOSI と MISO のワード |
| UART | 1 本 | ボーレート（auto で自動）、データビット 5〜9、パリティ、ストップビット、ビット順、反転 | バイトと文字、パリティ誤り（PE）、フレーミング誤り（FE）、ブレーク |
| パラレルバス | データ線（何本でも）、アドレス線、CS、RD、WR、クロック（データ線のほかはなくてもよい） | 線の並び（下の桁から。`0-7`、`0-7+9` など）、クロックのエッジ、CS / RD / WR のアクティブ、短いパルスを無視する幅 | 1 回のアクセスごとの読み書きの別、番地、値。一覧は続いたアクセスをまとめて 1 行 |
| CAN | 1 本（RX / TX のロジック信号か CANL） | ビットレート（auto で自動）、サンプル点、反転 | SOF、ID（標準 11 ビット / 拡張 29 ビット）、RTR、DLC、データ、CRC の照合、ACK / NACK、EOF、スタッフ誤り |

- **パラレルバスの値を取る時刻:**
  - RD や WR があるときは、そのストローブが終わる直前（アクティブの最後のサンプル）です。CS があれば、CS がアクティブの間だけ取ります。
  - RD も WR もなくクロックがあるときは、クロックのエッジの直前です。
  - どれもないときは、データ線かアドレス線が変わるたびに値を取ります。
- **サンプリングの速さ:** 信号のいちばん速いところの 4 倍以上（UART と CAN は 1 ビットに 10 サンプル以上）にします。
### 上位の解析（I2C の EEPROM / レジスタ、SPI フラッシュ、Modbus RTU）

I2C、SPI、UART の設定の「上位の解析」を選ぶと、バイトの並びに機器や規約の意味を付けた行が 1 本増えます。一覧も、その意味で出ます。

| 設定 | 下の解析 | 出るもの（例） |
|---|---|---|
| `eeprom` | I2C | `0x50 write 0x0010: A5 A6`、`0x50 read 0x0010: A5 A6`（番地だけ書いてから読む形）、`read (current address 0x0012)`、`no answer (NACK)` |
| `regs` | I2C | 同じ読み方で、レジスタとして出します（`0x68 read reg 0x75: 68`） |
| `flash` | SPI（CS と 8 ビットのワードが要ります） | 命令の名前、番地、データ。JEDEC ID はメーカー名と容量に直します（`Winbond (EF), type 40, capacity 18 (16 MiB)`）。ステータスは BUSY / WEL / BP に分けます |
| `modbus` | UART | 機器の番号、機能、番地と個数、値、例外、CRC の照合（`ID 1 Read holding registers -> 0x1234 0x004B`） |

- **I2C の番地のバイト数:** 「auto」では、EEPROM を 2 バイト（24C32 より大きいもの）、レジスタを 1 バイトとして読みます。24C01〜24C16 は 1 にします。
- **SPI フラッシュ:**
  - 番地は 3 バイトです。4 バイトの番地を使うものは、設定を 4 にします。0xB7 / 0xE9 の命令を見つけると、途中で切り替えます。
  - デュアルとクアッド（データ線が 2 本や 4 本）の読み書きは、命令と番地までは読めます。データ欄は、MOSI と MISO だけを見た値です。
- **Modbus RTU:**
  - バイトの間が 2.5 文字分より空いたところで、フレームを区切ります。
  - 要求か応答かは、長さで見分けます。機能 5 と 6（1 個書き込み）は、要求と応答が同じ形なので見分けません。
  - RS-485 の線には直接つなげません。トランシーバの RO か DI（ロジック信号）につなぎます。

- **CAN のつなぎ方:** CAN トランシーバの RX か TX（3.3V / 5V のロジック信号）につなぐのがふつうです。バスに直接つなぐときは、次のようにします。
  - CANL につなぎ、しきい値を「任意」で 2.0V にします。劣勢（リセッシブ）は 2.5V、優勢（ドミナント）は 1.5V なので、TX と同じ向きの信号になります。
  - CANH につなぐときは、しきい値を 3.0V にして「反転」を yes にします。
  - どちらの場合も、GND を CAN の機器とそろえます。
- **CAN FD:** 見つけると「CAN FD (not decoded)」と出します。中身はまだ読めません。
- **コマンドで:**

```
python3 decode.py cap.sr i2c:scl=0,sda=1 uart:rx=2,baud=115200 can:rx=3     # 1 通信 1 行
python3 decode.py cap.sr spi:clk=0,mosi=1,miso=2,cs=3,mode=0 --ann           # 枠をすべて
python3 decode.py cap.sr i2c:scl=0,sda=1,layer=eeprom spi:clk=4,mosi=5,miso=6,cs=7,layer=flash
python3 decode.py cap.sr uart:rx=0,baud=19200,parity=even,layer=modbus
python3 decode.py cap.sr parallel:data=0-12,addr=18-21,cs=22,rd=23,wr=24
python3 decode.py --help-specs                                               # 設定の一覧
```

### 解析が正しいかを確かめたこと

- **作った波形（`tests/synth.py`）:**
  - 作業用 PC の sigrok-cli の解析器と、結果を比べました。
  - I2C（100k / 400k、ACK と NACK、リピートスタート）、SPI のモード 0〜3、UART の 8N1 と 8E2、CAN（標準 / 拡張 ID、DLC 0〜8、NACK、すべて 0 / すべて 1 のデータ）で一致しました。
  - ただし sigrok（libsigrokdecode の can）は、DLC が 0 でないリモートフレームで、ないはずのデータを読みます。そのため、そこから後のフレームがずれます。こちらは規格どおりに、データを読みません。
  - 上位の解析も、sigrok の eeprom24xx、spiflash、modbus と比べて一致しました。
  - sigrok の modbus は、要求向きか応答向きかを決めて読みます。そのため 1 本の線では、両方の向きで 2 回読ませて比べました。
- **実機（`tests/atom_signals.py`）:** 上位の解析（EEPROM 風の I2C、SPI フラッシュの命令、Modbus）も確かめました。
  - AtomS3U から出した I2C、SPI、UART、CAN を取り込みました。
  - 送った中身と、解析の結果が一致しました。sigrok の結果とも一致しました。

```
cd ~/Claude/pokeana
python3 tests/synth.py /tmp/syn && python3 decode.py /tmp/syn/can.sr can:rx=0
sudo python3 tests/atom_signals.py mix      # AtomS3U: CH0/1 I2C（EEPROM 風）、CH2 UART、CH3 CAN
                                            # spi: SPI とフラッシュの命令、uart: CH0 文字列、CH1 Modbus、can、clk
```

- **長時間の試験（`tests/m2k_eeprom.py`、`tests/soak.sh`）:** ADALM2000 の DIO で、I2C の EEPROM（24FC256）4 個を同時に動かしました。
  - つなぎ方（SDA / SCL → ポケアナ、アドレス、速さ）: DIO8 / DIO1 → CH10 / CH9（0x53、100kHz）、DIO2 / DIO3 → CH11 / CH12（0x52、250kHz）、DIO4 / DIO5 → CH14 / CH15（0x51、125kHz）、DIO6 / DIO7 → CH16 / CH17（0x50、200kHz）。
  - 各組が、16 バイトの書き込みと、リピートスタートでの読み戻しを繰り返します。始まりは組ごとに毎回 0〜300µs ずらし、通信を重ねます。データには組の番号と通し番号が入っているので、解析の結果だけで正しいかを照合できます。
  - ADALM2000 の DIO0 は、パターンを出す動き方では変化しません（固定値は出せます）。そのため DIO8 を使っています。
  - オープンドレインの立ち上がりが遅く、SCL に 20〜100ns のひげが出ました。I2C の解析は、これより短いパルスを無視する設定（はじめは 150ns）で読みます。
  - 2026-11-21 23:40 から 12 時間、GUI の「連続」（10MHz、100 万サンプル、CH10 の立ち下がりでトリガ）で取り続けました。
    - 取り込み 42,187 回、書き込み 162,628 件と読み出し 168,748 件がすべて一致し、誤りは 0 でした。4 組が同時に通信していた取り込みは 40,657 回です。
    - GUI のメモリ（RSS）は 277〜408MB の間を上下し、増え続けることはありませんでした。
    - 書き込みの件数が少ないのは、トリガが読み出しの START でかかったとき、その回の書き込み（6ms 前）が取り込みの範囲（トリガ前 5ms）の外になるためです。

```
python3 tests/m2k_eeprom.py once /tmp/m2k.sr     # 1 回だけ動かし、pokeana.py で取り込んで照合
tests/soak.sh 12                                 # 12 時間（GUI は broadway の :5、結果は ~/soak/）
python3 tests/m2k_eeprom.py check ~/soak/dump.jsonl
```

- **パラレルバスの試験（`tests/nuc980_ebi.py`、`tests/nuc980_ebi/`、`tests/soak_ebi.sh`）:** NuMaker-Server-NUC980（NK-980ETH2P V1.2）の EBI を使いました。
  - つなぎ方: CON23 の D0〜D15 → CH0〜15、A0〜A3 → CH18〜21、nCS1 → CH22、nRE → CH23、nWE → CH24、VSS → GND。
  - ファーム（OS なし、NuWriter で DDR に送って動かす。フラッシュには書かない）は、bank 1 に 16 ビットで 16 回書いてから 16 回読み、約 2.5ms ごとに繰り返します。アクセス時間はいちばん長い設定（TACC=31）で、nWE と nRE の Low は約 210ns です。
  - 書く値には通し番号が入っていて、解析の結果だけで照合できます。読み出しは答える部品がないので、番地とストローブだけを照合します。
  - この基板では、A2（PB.2）が EBI のアクセスで動きません（High のまま）。また D13〜D15（PC13〜15）は、キー用の 0.1µF が付いていて追いつけません。照合は D0〜D12 で行います。
  - 2026-11-22 13:18 から 12 時間、GUI の「連続」（100MHz、100 万サンプル、CH22 の立ち下がりでトリガ）で取り続けました。
    - 取り込み 49,540 回、書き込み 198,160 件と読み出し 198,160 件がすべて一致し、誤りは 0 でした。
    - 1 回の取り込みの中で、ファームの通し番号は 148,620 回とも 1 ずつ続いていました（アクセスの取りこぼしなし）。
    - GUI のメモリ（RSS）は 377〜533MB の間を上下し、増え続けることはありませんでした。

```
python3 tests/nuc980_ebi.py load       # ファームをビルドして動かす（sudo、ボードは USB ブート待ち）
python3 tests/nuc980_ebi.py once       # 1 回取り込んで照合
tests/soak_ebi.sh 12                   # 12 時間（GUI は broadway の :5、結果は ~/soak_ebi/）
```

- **AtomS3U の CAN:** MicroPython には CAN（TWAI）を動かす機能がありません。そこで、フレームのビット列（スタッフビットと CRC を含む）をこちらで組み立てて、RMT で出しています。ACK は受け手がいるものとして、優勢で出します。

## 使い方（作業用 PC）

```
cd ~/Claude/pokeana        # replay_05.bin のある所
python3 pokeana.py --rate 20e6 --depth 100000 --pre 5000 --trigger 0=r -o cap.sr
python3 pokeana.py --skip-init --rate 2e6 --trigger 3=f,5=1 -o cap2.sr --view   # 2 回目から。終わったら PulseView で開く
sigrok-cli -i cap.sr -C CH00,CH01,TRIG -O ascii:width=120                      # 画面がなければ文字で
```

- `--rate`: 200MHz を整数で割った値です（200M、100M、66.7M、… 2M、…）。
- `--depth`: 全体のサンプル数です。2M サンプル（200MHz で 10ms）まで確かめました。
- `--pre`: トリガより前のサンプル数です。
- `--trigger`:
  - 「チャンネル=条件」をカンマで並べます。条件は `0`、`1`、`r`（立ち上がり）、`f`（立ち下がり）、`c`（変化）です。
  - `none` にすると、すぐにトリガがかかります。
  - 来なければ `--timeout` 秒（10 秒）で打ち切ります。そのときはメモリにある分を読みます。
- `--threshold`:
  - しきい値です。ボルト（−6〜6）か、LA Viewer の `ttl`（1.6V）、`ttl33`（1.49V）、`ecl`（−1.315V）で書きます。
  - `3.0,ttl` のようにカンマで 2 つ書くと、CH0〜17 と CH18〜35 を別々にできます。
  - 既定は `ttl` です。
- `--view`: 書き終わったら PulseView（`.sr`）か GTKWave（VCD）で開きます。画面のある所（作業用 PC のデスクトップの端末、または `ssh -X`）で使います。
- `--skip-init`: FPGA の書き込みを省きます。電源を入れて最初の 1 回は付けません（書き込みに約 0.7 秒かかります）。
- 動かすには USB の読み書きの権限が要ります。作業用 PC には udev の規則（`/etc/udev/rules.d/60-pokeana.rules`、`05e3:013b` を 0666 に）を入れたので、sudo は要りません。
- 仮想マシン（XP）にポケアナを渡したままだと使えません。仮想マシンから外してから使います（QEMU の `device_del pokeana`）。

## 起動の手順のデータ（replay_05.bin）は git に入れません

- ポケアナは、つなぐたびに本体の FPGA へ回路データ（約 6.8MB）を送ります。このデータは解読していません。LA Viewer が送ったバイト列を記録から取り出して、そのまま送り直しています。
- 中身はメーカーの FPGA の回路データなので、リポジトリには入れません（`.gitignore`）。`pokeana.py` と同じフォルダに `replay_05.bin` として置きます（`--replay` で場所を変えられます）。
- 作り直すときは、LA Viewer を起動するところから Run を押すまでを usbmon で記録して、次のように取り出します。

```
sudo tcpdump -i usbmon1 -s 0 -w start.pcap        # LA Viewer を起動して、Run を押すまで
python3 extract_replay.py start.pcap <デバイス番号> <Run までの秒数> replay_05.bin
```

LA Viewer では、メニューの Configure Environment を「FREQ <= 200MHz」にしてから記録しました。PicoVu 4GHz の取り込みは、まだ調べていません。

## わかった通信の形

USB 側は Genesys のブリッジ（`05e3:013b`）です。

- **ベンダー要求 0x04（値 0x82、8 バイト）:** 次のバルク転送の向きと長さを先に知らせます。
  - `01 00 82 00 長さ32` は PC から本体へ。
  - `00 00 82 00 長さ32` は本体から PC へ。
- **ベンダー要求 0x0C（値 0x8E、インデックス 0x20、IN 1 バイト）:** 準備ができたかを聞きます（01 が返ります）。
- **ベンダー要求 0x0C（値 0x83、1 バイト）:** ブリッジのレジスタです。LA Viewer は Run の前に `a5 f2 f6 f0 a7 ab f2 a7` を、読み出しの後に `f2 a7` を書きます。
- **本体への命令:** バルク OUT（EP2）で送ります。どれも `5a 00 0f 00 66 00` + 16 ビットの番号 + 引数、の形です。

| 番号 | 意味 |
|---|---|
| 22 v32 | 次のレジスタ書き込みの値を置く |
| 0f | 番地。Run では書き始め（−トリガ前の数）、読み出しでは読み始め |
| 06 | トリガ後のサンプル数 |
| 24, 25 | サンプリングの分周。200MHz ÷ (n+1) |
| 29, 0a | いつも 0 |
| 02 + 784 バイト | トリガ表 |
| 01 / 00 | スタート / ストップ |
| 30, 03 | 読み出し |
| 20 0, 04 | 状態（36 バイト返る） |
| 21 + 32 バイト | しきい値。ブリッジに 96 を書いてから送り、00 を書いて終わる |
| 07 a b c | 2 本の線（a のビット 7 と 6）で約 1460 ビットを送る。LA Viewer は起動して最初の Run の前に送る。中身は不明で、記録から送り直す |

- **状態（36 バイト）:**
  - 0 バイト目: フラグです。ビット 0 はトリガがかかって取り込みが終わったことを表します。
  - 2〜4 バイト目: 書き込み中の番地です。
  - 6〜9 バイト目: トリガ後の残りの数です。
  - 10 バイト目から: 今の入力の値です。
- **しきい値（21）:**
  - 4 バイトの DAC の値（CH0〜17、CH18〜35、CH0〜17、CH18〜35）のあとに、0 が 28 バイト続きます。
  - 値は 13 が −6V、235 が +6V の直線です（1 段 54mV）。LA Viewer の TTL は 0x99、TTL 3.3 は 0x97、ECL は 0x64 です。
  - AtomS3U（High は約 3.2V）で確かめました。3.0V までは正しく取れ、3.2V ではばたつき、3.4V では 0 のままです。−1V にすると、開いているチャンネルも 1 になります。
- **USB の構成:** 開くたびに構成（set_configuration）をし直すと、ホスト側のデータトグルだけが戻ります。本体側は戻らないので、最初に読む 1 パケットが捨てられ、状態の読み取りが 5 秒待って失敗していました。今は、構成がまだ 1 でないときだけ設定します。
- **サンプル:** 1 つが 8 バイト（リトルエンディアン）で、ビット n がチャンネル n です。メモリは 2M サンプルの輪になっています。
  - 記録は 3 サンプル遅れて入ります。
  - 読み出しの最初の 5 語は古い値です（`LAG`、`STALE`）。
- **トリガ表:** 比べる組が 2 つあります。それぞれ「直前の値」と「今の値」のパターンに、マスクが付きます。
  - 置き場所: パターンは 92、98、188、194 バイト目から、マスクは 476、482、572、578 バイト目からで、どれも 6 バイトです。
  - 779 バイト目: レベルだけなら c0、エッジがあると f0 です。ビット 7 でトリガが有効になり、ビット 5〜4 でエッジ検出の回路が動きます。ビット 5〜4 を 0 にしておいて有効にすると、最初の 1 サンプルを古い値と比べてしまい、エッジでない所でかかることがあります。
  - 783 バイト目: 「変化」で f0 です（2 組目のパターン用で、779 と同じ意味）。
  - 2 組のパターンは OR です。「変化」は 1 組目が立ち上がり、2 組目が立ち下がりです。
  - 走っている間にも表を送り直せます。
- **トリガ前の分:** 本体は、走り始めた最初のサンプルからトリガを受け付けます。そのため、このツールでは次のようにしています。
  - まず 779 バイト目（変化なら 783 バイト目も）を 30 にした表で走らせます。エッジ検出は動きますが、トリガはかかりません。
  - `--pre` の分を書き終わる時間だけ待ってから、本物の表を送ります。
  - 状態の 0 バイト目のビット 6 は、トリガ前の分とは関係ありませんでした。
